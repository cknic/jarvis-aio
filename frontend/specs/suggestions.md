# View spec: `suggestions`

Derived from the old panel's `data-tab="suggestions"` tab (`custom_components/jarvis/frontend/jarvis-panel.js`,
`_renderSuggestions()` ~L2853, wiring ~L6393) plus the Goals card (`_renderGoals()` ~L2810, wiring ~L6423-6478) and the
Cognitive-core learning readout / "Analyze Now" button (~L1343-1375, ~L4617, ~L6598-6655). In the OLD panel the Goals card
and the learning readout lived on the dashboard ("Command Center") tab, not on the suggestions tab; this spec moves them
here because they are the same feature family (what JARVIS has learned / is working toward) and the new dashboard spec
does not carry them. Everything a view implementer needs is in this file; do not read the old panel.

Route: `/jarvis/suggestions` (HA `route.path === "/suggestions"`). Nav label: **Suggestions**. Admin-only (whole panel is).
Implementation: `<jarvis-view-suggestions>` (`src/views/suggestions.ts`, a thin layout that owns the toast region) over
`src/views/suggestions/`: `suggestion-list.ts` (`<jarvis-suggestions-list>`, L1), `goals-card.ts`
(`<jarvis-suggestions-goals>`, L2), `learning-card.ts` (`<jarvis-suggestions-learning>`, L3), `format.ts`, `types.ts`.

---

## Purpose

Let the admin review the automations the pattern engine has learned from household behaviour and decide, one by one,
whether to **install** each into Home Assistant or **dismiss** it, seeing the exact automation payload and the evidence
first. Nothing is created in HA without an explicit approve click. Secondary: manage **goals** (long-running outcomes
JARVIS pursues autonomously: add, cancel, delete) and show **routine-learning status** (how much data the engine has, when
it last analysed, with a manual "Analyze now" trigger that reports what it found or why it did not run).

---

## Data

All commands are HA WebSocket commands sent through the panel's `ws(hass, type, payload)` helper (`src/ws.ts`, wrapping
`hass.callWS`). Every one is `@websocket_api.require_admin`. Error responses arrive as a rejected `WsError` whose
`.message` is the handler's error message string and `.code` the error code given below.

### D1. `jarvis/get_panel_data` (snapshot; the view reads only `suggestions` and `goals`)

Request:
```json
{ "type": "jarvis/get_panel_data" }
```
No other fields.

Response: a large object (`panel_data.build_snapshot()` merged with a `config` sub-dict). This view uses two
top-level keys:

`suggestions: Suggestion[]` (`panel_data._get_suggestions`; pending rows only, ordered by `confidence DESC`, max 20;
never raises, returns `[]` on any failure):

| field | type | notes |
|---|---|---|
| `id` | `int` | sqlite row id; the `suggestion_id` for D2 |
| `created` | `str` | ISO-8601 local timestamp, e.g. `"2026-10-28T19:02:11.123456"`; may be `""` |
| `description` | `str` | one-line human description generated by the engine |
| `yaml` | `str` | **Despite the name this is a JSON text blob**, not YAML. The stored `automation_yaml` column holds `json.dumps({...})` of an automation-like object: `{alias, description?, trigger, condition?, action, mode?}` using legacy keys (`platform` in triggers, `service` in actions), OR an advisory marker `{"type":"manual_review","note":"..."}` / an object with `note` and no `trigger`. May be `""`. See *Layout* for how to show it. |
| `confidence` | `float` | 0..1, rounded to 2 dp |
| `count` | `int` | `pattern_count`: observed occurrences in the 30-day window; `0` if unknown |
| `pattern_type` | `str` | one of `"time_routine"`, `"sequence"`, `"confirm_sequence"`, `"numeric_trigger"`, `"repeated_command"`, `"temp_pref"`, `"presence"`, or `""`/unknown |
| `entities` | `str[]` | entity_ids involved (parsed from JSON column); may be `[]` |
| `why_headline` | `str` | `explain_suggestion().headline`, e.g. `"A daily routine around 19:00"`, `"One action reliably follows another"`, `"⚠ A confirmed sequence (safety-sensitive)"`, `"A threshold routine"`, `"A command you give often"`, `"A temperature preference"`, `"A presence-linked pattern"`, `"A learned pattern"`; may be `""` |
| `evidence` | `str[]` | `explain_suggestion().evidence`: 1..6 plain-English observation lines (e.g. `"Happened on 12 of 14 days (missed 2)"`, `"Seen 7 times in 30 days"`, `"Only while Kitchen occupancy is occupied"`); may be `[]` |

`goals: Goal[]` (`panel_data._get_goals`; `goals.recent(limit=20)`: ALL statuses, ordered by `updated_ts DESC`;
never raises, `[]` on failure):

| field | type | notes |
|---|---|---|
| `id` | `int` | the `goal_id` for D3 |
| `title` | `str` | short title; backend defaults it to first 60 chars of `outcome` when created without one |
| `outcome` | `str` | the outcome JARVIS works toward (user text, max 240 chars from the panel) |
| `status` | `str` | `"active"` \| `"done"` \| `"failed"` \| `"cancelled"` |
| `steps_done` | `int` | count of steps with `status == "done"` |
| `steps_total` | `int` | `len(steps)`; may be `0` (goals created from the panel have no steps until the runner adds them) |
| `steps` | `Step[]` | `{n:int, step:str, status:"pending"\|"done"\|"failed"\|"skipped", note:str}` |
| `next_check_ts` | `str` | `"YYYY-MM-DD HH:MM:SS.ffffff"` (ISO with a SPACE separator, local time); may be `""` |
| `deadline_ts` | `str \| null` | same format or `null` |
| `last_result` | `str` | runner's last outcome text; `""` when none |
| `updated_ts` | `str` | same timestamp format |

**Timestamp parsing:** goal timestamps use a space separator; parse with `new Date(s.replace(" ", "T"))` and treat
`NaN` as "unknown". Suggestion `created` uses `T` already.

When fetched: the shell fetches the snapshot on panel load and re-polls every **20 s** (old panel: `setInterval(_fetchLiveData, 20000)`).
The view renders from the shared snapshot store; it must NOT trigger its own snapshot poll. After a successful D2 or D3
action the view asks the shell for an immediate re-fetch (D3 already returns the fresh `goals` list; use it directly and
still request a snapshot refresh so other views stay consistent).

**Live-refresh guard (carry over):** the old panel skipped full DOM rebuilds while the suggestions tab was open so a
poll never wiped an expanded YAML preview or an in-progress goal input. In Lit this means: keep "expanded" state and the
goal input value in component state keyed by `suggestion.id`, not in the DOM, so a re-render from a fresh snapshot
preserves them.

### D2. `jarvis/suggestion_action`

Request (voluptuous schema, exactly):
```python
{
    vol.Required("type"): "jarvis/suggestion_action",
    vol.Required("suggestion_id"): int,
    vol.Required("action"): vol.In(["approve", "dismiss"]),
}
```

Response, `action == "approve"` (`install_approved_suggestion`):
```ts
{ ok: boolean, installed: boolean, reason: string | null, alias: string | null }
```
- `installed: true` → the automation was written to HA; `alias` is its name; `reason` is `null`.
- `ok: true, installed: false` → the suggestion was marked *approved* (acknowledged) but nothing was written; `reason`
  is one of the normaliser's strings: `"no automation payload"`, `"payload is not valid JSON"`,
  `"payload is not an object"`, `"advisory only — needs a human to design the automation"`,
  `"missing alias, trigger, or action"`, `"no actuating action — target is a read-only entity"`,
  `"automation write failed: <error>"`, or `"not installable"`. `alias` is `null`.
- `ok: false` → `reason` and `alias` are `null`; the install helper swallowed its own error (e.g. `suggestion #N not found`).
  The error text is NOT relayed (the helper's `error` key is dropped by the handler). Treat as failure.
- Side effect: on success the row's status becomes `installed` or `approved`, so it disappears from `suggestions` on
  the next snapshot.

Response, `action == "dismiss"`:
```ts
{ ok: boolean }
```
`ok: false` means the DB update failed (row still pending).

Error (either action, exception path): `send_error(code="suggestion_action_failed", message=str(exc))`.

### D3. `jarvis/goal_action`

Request (voluptuous schema, exactly):
```python
{
    vol.Required("type"): "jarvis/goal_action",
    vol.Required("action"): vol.In(["cancel", "delete", "create"]),
    vol.Optional("goal_id"): int,
    vol.Optional("title"): str,
    vol.Optional("outcome"): str,
    vol.Optional("interval_min"): vol.Coerce(float),
}
```
The old panel sends only: `{type, action:"create", outcome}` and `{type, action:"cancel"|"delete", goal_id}`.
`title` and `interval_min` are accepted but were never sent from the panel (backend defaults: title = first 60 chars of
outcome; check interval 30 min, clamped to 1..1440).

Response, `create`:
```ts
{ ok: true, goal: { id:int, title:str, outcome:str, steps:Step[], next_check_ts:str, deadline_ts:string|null }, goals: Goal[] }
```
(`goal` is the raw `goals.create()` row, NOT panel-shaped: no `status`, `steps_done`, etc. Use `goals` for rendering.)

Response, `cancel` / `delete`:
```ts
{ ok: boolean, goals: Goal[] }
```
`ok: false` for cancel means no row was active with that id (already closed); for delete, no row with that id.

Errors (`send_error`):
- `create` with blank/whitespace `outcome` → code `"empty_outcome"`, message `"a goal needs an outcome to work toward"`.
- `create` when `goals.create()` returns `{error}` → code `"create_failed"`, message e.g. `"goal list is full (10 active)"`
  (MAX_ACTIVE = 10) or a DB error string.
- `cancel`/`delete` without `goal_id` → code `"missing_goal_id"`, message `"<action> needs a goal_id"`.
- any exception → code `"goal_action_failed"`, message `str(exc)`.

Semantics: **cancel** keeps the row (status → `cancelled`) for history; **delete** hard-removes the row (any status).
The old UI offered cancel only for `active` goals and delete only for non-active ones.

### D4. `jarvis/get_cognitive_status` (learning status card)

Request: `{ "type": "jarvis/get_cognitive_status" }`

Response (`cognitive_core.status()`), fields this view uses:
```ts
{
  running: boolean,
  learning: {                      // StateLogger.get_pattern_stats(); {} if the logger is not running
    state_changes: int,            // rows in state_changes
    commands: int,                 // rows in commands
    suggestions: int,              // pending suggestions (same count as snapshot.suggestions.length)
    patterns: int,                 // person_patterns rows
    days_of_data: int              // days since oldest state_change
  },
  ignore_rules: int,
  last_analysis: {                 // analyzer._last_result; {} if never ran this HA session
    ts: float,                     // unix seconds
    patterns_found: int,
    new_suggestions: int,
    person_routines: int,
    facts: int,
    near_misses: NearMiss[]        // see D5
  },
  // also present, NOT used here: tick_count, actions_taken, offers_made, autonomous_actions,
  // autonomy_grants[], uptime_hours, last_tick_ago, certification{}
}
```
Failure path (handler catches): `{ running:false, error:str, learning:{} }` sent via `send_result` (not an error frame).

When fetched: once when `hass` first arrives, again on every new snapshot (the shell's 20 s tick — cheap: two sqlite
counts), and after every D5 run.

### D5. `jarvis/run_analysis` ("Analyze now")

Request: `{ "type": "jarvis/run_analysis" }`

Response (`cognitive_core.run_analysis_now`), always via `send_result`:

Did not run (data gate: needs ≥ 7 days AND ≥ 50 recorded changes):
```ts
{ ran: false, reason: string, days_of_data: int, state_changes: int, backfill: Backfill }
```
`reason` = `"Not enough history yet — pattern learning needs about a week of data (≥ 7 days and ≥ 50 recorded changes)."`

Ran:
```ts
{
  ran: true,
  ts: float, patterns_found: int, new_suggestions: int, person_routines: int, facts: int,
  near_misses: { type:str, description:str, occurrences:int, needed:int|null }[],   // max 8
  state_changes: int, days_of_data: int,
  backfill: { imported:int, entities:int, considered:int },   // may be {} on backfill failure
  diagnostic: {                                                // may be {} on failure
    top_sources: { entity_id:str, changes:int }[],             // max 10
    candidates: { entity_id:str, state:str, hour:int, occurrences:int, days:int, coverage:float }[],  // max 12
    total_days: int, min_days: int, min_occurrences: int
  }
}
```
Handler exception path: `{ ran:false, error:str }`.

The call can take several seconds (recorder backfill + analysis); show a busy state on the button.

### Settings keys (read from `snapshot.config`, written via `jarvis/update_config`)

The old suggestions tab wrote **no** settings. The related learning toggles lived on the Settings tab and belong to the
`settings` view, category `learning` in `config_apply.py`: `pattern_learn_doors`, `pattern_learn_presence`,
`pattern_learn_buttons`, `pattern_learn_motion` (bool), `pattern_include_entities` (list), `pattern_min_occurrences`
(int 1..50, default 4), `pattern_confidence` (float 0..1 step 0.05, default 0.55), `suggest_garage_confirmation` (bool,
had a confirm dialog), `adaptive_suggestion_threshold` (bool). This view does not write any of them; it may deep-link
to the settings view's learning section (see Layout L4).

### `hass.callService` calls
None. The old suggestions tab, Goals card and Analyze button used no service calls.

## Layout

Single scrollable column at phone width; two columns ≥ 900 px (left: L1 + L2; right: L3 + L4). Cards are `<jv-section>`
surfaces with `--jv-*` tokens only (DESIGN.md); chips are `<jv-state-badge>`, key/value rows `<jv-kv>`.

### L1. Suggestions card — PRIMARY (first on mobile)

Header: **"Suggestions"** with a count chip on the right: `"{n} to review"` (hidden when 0).
Intro line (muted, collapsible on mobile after first visit is NOT required; just keep it short):
> Automations JARVIS has learned from watching your routines. Approve to create one in Home Assistant, or dismiss it. Nothing runs until you approve.

List of suggestion items, in the order received (backend already sorts by confidence desc). Each item:

1. **Type chip** (left) from `pattern_type`:
   `time_routine → "Daily routine"`, `sequence → "Action sequence"`, `repeated_command → "Repeated command"`,
   `temp_pref → "Temperature"`, `presence → "Presence"`, `numeric_trigger → "Sensor threshold"`,
   `confirm_sequence → "Confirmed sequence"` (render with a warning tone; it is safety-sensitive: it closes a cover),
   anything else → `"Learned pattern"`.
2. **Confidence** (right): `"{pct}% confident"` where `pct = Math.round(confidence*100)`; tone: `≥80` success,
   `55..79` warning, `<55` muted; plus a thin linear progress bar at `pct`.
3. **Headline** `why_headline` (semibold) when non-empty.
4. **Description** `description` (body text).
5. **Evidence**: label **"What JARVIS observed"** then a bullet list of `evidence` lines; omit the block when empty.
6. **Entities**: `entities` as small monospace chips; omit when empty. (Optional nicety: show
   `hass.states[eid]?.attributes.friendly_name` as a title/tooltip; the id stays the chip text.)
7. **Seen line** (muted): `"Seen {count}× in 30 days"`; if `count` is 0/missing show `"Seen ?× in 30 days"` as the old
   panel did, or omit the line (implementer's choice; omitting is preferred).
8. **Actions row**: primary button **"Create automation"**, secondary **"Dismiss"**, text button **"Show automation"**
   which toggles to **"Hide automation"**.
9. **Automation preview** (collapsed by default): a `<pre>` with the parsed-and-pretty-printed payload. Parse `yaml`
   with `JSON.parse`; on success `JSON.stringify(obj, null, 2)`; on failure show the raw string. If the parsed object
   is an advisory marker (`type === "manual_review"` or has `note` and no `trigger`) show a note above the pre:
   **"Advisory only — approving records your acknowledgement but installs nothing."** and relabel the primary button
   **"Acknowledge"**. If `yaml` is empty show **"No automation payload."** instead of a pre. Escape text; never
   `innerHTML` the payload. (Do not try to convert to real YAML in Phase 2; the backend calls it yaml but stores JSON.)

Mobile: the actions row wraps; "Create automation" spans full width first, Dismiss and Show automation share a second
row.

### L2. Goals card

Header: **"Goals"** with chip `"{activeCount} active"`.
Input row: text field placeholder **"Give JARVIS a goal to work toward…"** (`maxlength=240`) + button **"Add"**.
Enter in the field submits. Field and button disabled while the create call is in flight.

List (order as received: most recently updated first). Each goal item:
- Status badge: `active → "Active"`, `done → "Done"` (success), `failed → "Failed"` (error), `cancelled → "Cancelled"`
  (muted), else the raw status capitalised. Non-active items render at reduced emphasis (old: opacity .5–.7).
- `title` (semibold) and `outcome` (body).
- When `steps_total > 0`: progress bar at `round(steps_done/steps_total*100)` and text `"{steps_done}/{steps_total} steps"`.
- "When" line (muted): for active goals `"Deadline {rel}"` if `deadline_ts` else `"Next check {rel}"` where `rel` is a
  relative time (`"in 12m"`, `"3h ago"`, `"in 2d"`; empty string when unparseable → omit the line). For non-active goals
  show `last_result` when non-empty.
- Trailing icon button: active → **cancel** (`mdi:close`, title "Cancel this goal"); non-active → **delete**
  (`mdi:delete-outline`, title "Delete this goal").

### L3. Routine learning card

Header: **"Routine learning"**. Body from D4:
- Row **"Data"**: `"{days_of_data} days"`; **"State changes"**: `state_changes`; **"Commands"**: `commands`;
  **"Pending suggestions"**: `learning.suggestions`; **"Ignore rules"**: `ignore_rules`.
- Row **"Last analysis"**: if `last_analysis.ts` → `"{ago} · {patterns_found} found, {new_suggestions} stored"` with
  `ago` as `"{m}m ago" | "{h}h ago" | "{d}d ago"`; else **"Not yet this session"**.
- Button **"Analyze now"** (outlined). While running: disabled, label **"Analyzing…"**, helper text
  **"Running pattern analysis over your history…"**.
- Result area (persists until the next run or view change), from D5:
  - `ran:true`: `"Found {patterns_found} patterns, {new_suggestions} new suggestions."` If `new_suggestions > 0` append
    **"They're listed above."**; else append **"Nothing cleared the confidence bar this pass."** and, when present:
    - closest candidate (`diagnostic.candidates[0]`): `"Closest routine: {entity_id} → {state} ~{HH}:00, seen {days}/{total_days} days (needs {min_days})."`
    - busiest source (`diagnostic.top_sources[0]`): `"Busiest source: {entity_id} ({changes} changes)."`
    - near misses (up to 5): heading **"Building toward suggestions:"** then `"{description|type} ({occurrences}/{needed})"`
      or `"({occurrences}×)"` when `needed` is null.
    - backfill note when `backfill.imported > 0`: `"Imported {imported} past events from history for {entities} new entities."`
  - `ran:false`: show `reason || error || "Analysis did not run."` as an error-toned line (plus the backfill note if any).
  - WS rejection: show `err.message`.
  - After any completed run: refetch D4 and ask the shell to refresh the snapshot (new suggestions appear in L1).

### L4. Footer link
Text link **"Learning settings"** → `this.navigate("settings", "learning")` (the shell turns that `jarvis-navigate`
into `/jarvis/settings/learning`, which opens the Learning category).

Mobile primary order: L1, L2, L3, L4.

## States

- **Loading** (no snapshot yet): L1 and L2 show skeleton rows (3 and 2); L3 shows skeleton rows until D4 resolves.
- **Empty suggestions**: L1 body shows icon `mdi:lightbulb-outline`, title **"No suggestions right now"**, and body
  **"JARVIS proposes automations as it notices routines repeat — a light you turn on each evening, a scene after a button
  press, the heat when it's cold. As patterns build up, they'll appear here for you to review and approve. Nothing is
  ever created without your say-so."** Count chip hidden.
- **Empty goals**: list area shows **"No goals yet. Add one above, or ask JARVIS to set one."**; input stays usable.
- **Error** (snapshot fetch failed): handled by the **shell** for every view (an error alert with the message and a
  "Retry" button above the view; the last snapshot stays rendered). L1/L2 render no error of their own (the string
  "Couldn't load panel data" is not used). L3 on D4 failure/`error` field: show **"Learning status unavailable"** (+
  `error` text when present); "Analyze now" remains enabled.
- **Disabled**: D4 `running:false` → L3 shows a muted line **"Cognitive core is not running"**; keep "Analyze now"
  enabled (it still works; it only needs the state logger, and returns a reason if not). Suggestion/goal buttons are
  disabled only while their own call is in flight or after a successful A1/A2 until the next snapshot.
- **Stale after action**: after A1/A2 the item remains (faded) until the 20 s poll or the requested refresh removes it;
  do not splice it client-side (keeps the "approved — advisory" toast context visible).
- **Narrow**: `narrow === true` → single column; chips wrap; action buttons stack as in L1.

## Dropped to Phase 3

- **Per-person routines** (`jarvis/get_person_routines`, response `{routines: {person: [{id, pattern_type, description, confidence, occurrences, last_seen}]}}`): old panel showed them on the Memory tab, not here; the Memory view shows them (memory.md §3.2).
- **Suggestion threshold / calibration readout** (`jarvis/get_calibration` → `suggestion_threshold {base, effective, learned_delta}`, `suggestion` outcome rate): dashboard diagnostics in the old panel; low value for the review flow.
- **Learning toggles & thresholds** (`pattern_learn_*`, `pattern_include_entities`, `pattern_min_occurrences`, `pattern_confidence`, `suggest_garage_confirmation`, `adaptive_suggestion_threshold`): stay in the settings view; this view only links there. The calibration readout is on the Logs view (System Diagnostics › Judgment calibration).
- **Goal `title` / `interval_min` inputs and step-level display**: backend supports them (D3 schema; `steps[]` in the snapshot) but the old panel never exposed them; a steps accordion is a Phase 3 nicety.
- **Suggestion history** (approved / installed / dismissed rows): no WS command returns them (`get_pending_suggestions` is pending-only); would need a backend change.
- **Real YAML rendering of the automation payload**: payload is JSON; converting to YAML client-side needs a library and the backend may later change the shape; pretty JSON is enough for Phase 2.
- **Entity friendly-name chips with click-through to HA more-info**: nice-to-have, depends on shell helpers.

## Risks

- **`yaml` is JSON.** Field name and old UI label ("See the automation") imply YAML, but `automation_yaml` holds `json.dumps(...)`. Implementers must `JSON.parse`, not feed it to a YAML highlighter. Legacy keys (`platform`, `service`) appear in the stored blob; the installer modernises them, the preview shows them as stored.
- **Advisory payloads are indistinguishable from the list alone**: there is no `installable` flag in the snapshot. The view can only infer "advisory" from the payload shape (`type:"manual_review"` or `note` without `trigger`); other non-installable cases (`missing alias…`, `read-only entity`) are only known after approve returns `installed:false`. UI must handle `ok && !installed` gracefully for every type.
- **Approve `ok:false` loses the error text**: handler returns `{ok:false, installed:false, reason:null, alias:null}` and drops the helper's `error`. The view can only show a generic failure.
- **Snapshot does not splice approved/dismissed rows**; the row persists until the next 20 s poll. If the shell exposes a manual refresh, call it after A1/A2.
- **Goal timestamps use a space separator** (`"2026-10-29 08:15:00.123456"`), unlike suggestion `created` (`T`). `deadline_ts` may be `null`; `next_check_ts` may be `""`.
- **`steps_total` is 0 for panel-created goals** until the headless runner populates steps; progress UI must be conditional.
- **Goals list cap**: `recent(limit=20)` means old done/failed goals silently drop off; MAX_ACTIVE is 10 (`create_failed`, "goal list is full (10 active)").
- **`last_analysis` is per-HA-session** (in-memory `_last_result`); after a restart it is `{}` even though analyses ran before.
- **`get_cognitive_status.learning` may be `{}`** when the state logger is not running; treat all counts as 0.
- **D5 can be slow** (recorder backfill up to 30 days, capped) — give it a generous timeout and a visible busy state; do not run it on view mount.
- **`confirm_sequence` type** exists in the backend (`explain_suggestion`) but had no label in the old TYPE_LABEL map (fell through to "LEARNED PATTERN"); this spec adds "Confirmed sequence" with warning tone.
- **i18n casing**: existing keys are "Routine Learning" and "Analyze Now" (title case); using different casing loses the 23 translations.
- **Old `_localizeDOM` translated by walking text nodes**; the new view must call `t()` explicitly per string and must not rely on a DOM walk.
